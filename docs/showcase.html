lumen.css

A CSS-only, CSS-variable-configurable, semantic-first framework for productive business applications. No startup classes required. Drop in one <link> tag and your semantic HTML looks great.

Token contract

All customisation happens by overriding semantic tokens on :root. Primitive tokens (--_*) are internal and subject to change. The table below shows the stable public API.

Colour tokens (partial list)
Token Swatch Role
--color-bg Page background
--color-surface Card / panel background
--color-text Primary text
--color-accent Interactive accent / primary actions
--color-danger Error / destructive state
--color-success Positive / completed state
--color-warning Caution state
--color-border Default border
How to customise the theme

Override any semantic token on :root before or after the framework import: 

:root {
  --color-accent:       #7c3aed;
  --color-accent-hover: #6d28d9;
  --font-family-base:   "Inter", system-ui, sans-serif;
}

The dark theme derives automatically from the same semantic tokens via @media (prefers-color-scheme: dark). To force a mode, set data-theme="dark" or data-theme="light" on <html>.

Field composition primitives

data-field and data-field-row are narrow opt-in wrappers that solve what native HTML alone cannot: a consistent way to associate a label, help text, error message, and success message with a single control or a grouped set of controls. They are not general layout utilities.

The API uses three child marker attributes: [data-help], [data-error], and [data-success]. These must be direct children of [data-field]. Validation semantics remain native-first through :invalid and aria-invalid; the wrappers only present those states coherently.

Framework scope (what lumen.css does not own)

  • Validation logic — application code decides when a field is invalid and sets aria-invalid.
  • Visibility management of [data-error] and [data-success] markers — show or hide them as needed.
  • Multi-step or wizard layouts — those belong to application layout code.
  • Input groups, prefix/suffix addons, or floating label patterns — see the Input group section.

Input group composition

data-input-group is a narrow opt-in composition wrapper for common production controls. It presents the group as one cohesive surface: a shared border, a unified focus ring, and propagated invalid and disabled states.

Four supported patterns in v1: leading icon search field, currency prefix field, suffix unit field, and trailing action button field. Each must have an associated <label> — prefix and suffix markers are aria-hidden and purely decorative.

Authoring rules

  • Host must be div[data-input-group].
  • Exactly one text-like control per group: input (not checkbox, radio, range, file, color), select, or button as the primary element.
  • [data-prefix], [data-suffix], and [data-icon] must be non-interactive elements (e.g. span) with aria-hidden="true".
  • Every input group must be paired with a visible <label for="…"> — never rely on placeholder text alone for identification.

Framework scope (what lumen.css does not own)

  • Search submission — wire up the form or button click yourself.
  • Clear-button behaviour — resetting or clearing a field is application logic.
  • Unit conversion — the suffix label is decorative; conversion lives in application code.
  • Input masking — currency formatting, phone formatting, and similar masks are application code.
  • Validation messaging — combine data-input-group with div[data-field] for label, help text, and error message composition.

Navbar pattern (nav[data-navbar])

The primary navigation contract is nav[data-navbar] inside header[data-layout-header]. It contains one or two direct <ul> elements — the first is the primary/start group, the second optional <ul> is the secondary/end group.

Top-level items are li > a for plain links or li > button + ul for single-level grouped navigation that opens on hover and focus. Use aria-current="page" on active links.

At widths above 48 em the navbar is always visible inline and the toggle is hidden. At or below 48 em the toggle becomes visible and the navbar collapses until aria-expanded="true" reveals it as a full-width stacked panel below the header. lumen.css owns only presentation; application code owns toggle events and aria-expanded state.

Authoring contract

  • header[data-layout-header] — required host (inside div[data-layout-shell]).
  • button[data-nav-toggle][aria-expanded][aria-controls] — optional toggle; must carry aria-expanded and aria-controls pointing to the nav id.
  • nav[data-navbar][id] — the navigation element; id is required when a toggle is present.
  • nav[data-navbar] > ul — primary group (left/start aligned).
  • nav[data-navbar] > ul:nth-child(2) — secondary group (right/end aligned, optional).
  • li > a[href] + ul — single-level grouped navigation; the a is both a navigation link and the dropdown trigger; opens on hover or focus-within, no JavaScript required.
  • div[data-layout-actions] — optional last child of the header for action buttons.

Framework scope (what lumen.css does not own)

  • Toggle click handler — set aria-expanded yourself.
  • Escape-to-close — application code adds the keydown handler.
  • Open-state persistence across page loads.
  • Roving focus / keyboard navigation within the open panel.

Layout shell (div[data-layout-shell])

div[data-layout-shell] is a container-based full-height layout wrapper that supports exactly eight direct-child combinations without any extra CSS. All variants are detected automatically via :has() — no modifier class or attribute is required on the host.

Direct child roles (in document order): optional header[data-layout-header], optional aside[data-layout-sidebar], required main, optional aside[data-layout-panel], optional footer[data-layout-footer].

Supported variant matrix

# Combination Desktop layout
1 main Single full-height content region
2 header + main Sticky header, scrollable main
3 header + main + panel Sticky header, main + fixed-width right panel
4 header + main + footer Sticky header, scrollable main, sticky footer
5 header + sidebar + main Sticky header, fixed-width left sidebar, scrollable main
6 header + sidebar + main + panel Sticky header, sidebar, main, right panel
7 header + sidebar + main + footer Sticky header, sidebar, main, sticky footer
8 header + sidebar + main + panel + footer Full shell: header, sidebar, main, panel, footer

Deferred (not supported in this release): main + footer, main + panel, header + main + panel + footer, sidebar + main, and sidebar + main + footer are intentionally out of scope. Headerless sidebar variants leave narrow-width sidebar discoverability under-specified; other combinations add documentation cost without distinct product value.

Authoring contract

  • div[data-layout-shell] — required host; can be placed anywhere in the document (not just on <body>).
  • header[data-layout-header] — optional; spans the full top row; sticky.
  • aside[data-layout-sidebar] — optional; fixed-width left track; independently scrollable. At ≤ 48em it goes off-canvas; revealed with data-open.
  • main — required; fluid center track; the sole vertical scroll region for primary content.
  • aside[data-layout-panel] — optional; fixed-width right track; hidden and track collapsed at ≤ 48em. Presence is auto-detected via :has().
  • footer[data-layout-footer] — optional; spans the full bottom row; sticky.

Responsive behavior

  • At ≤ 48em: aside[data-layout-sidebar] slides off-screen (transform: translateX(-100%)). Add data-open to reveal it.
  • At ≤ 48em: aside[data-layout-panel] is hidden and its column track is collapsed so main fills the full width.
  • At ≤ 48em: nav[data-navbar] collapses; toggle button becomes visible.
  • prefers-reduced-motion: reduce disables sidebar and navbar transitions.

Framework scope (what lumen.css does not own)

  • Sidebar toggle wiring — application code manages the toggle button, sets data-open on the sidebar, and updates aria-expanded.
  • Navbar toggle wiring — application code sets aria-expanded on [data-nav-toggle].
  • Panel show/hide — application code decides when to include or remove aside[data-layout-panel].
  • Overlay/scrim — no backdrop is provided for the off-canvas sidebar.

Breadcrumb navigation

A semantic breadcrumb trail that gives deep application screens orientation and hierarchy. Scope is intentionally restricted to nav[data-breadcrumbs] — it does not affect generic <nav>, navbars, or ordered lists.

Presentation only. Application code owns route generation and localized crumb labels. Separators are decorative CSS — they are never written into the DOM.

Authoring contract

The only supported host is nav[data-breadcrumbs] with either aria-label or aria-labelledby. The direct child is exactly one <ol>. Each <li> represents one location step. The current page is marked only with aria-current="page" on the last item.

  • a[href] — ancestor location step (interactive).
  • a[href][aria-current="page"] — current page, link variant (still interactive).
  • span[aria-current="page"] — current page, non-interactive variant.

Loading patterns

Four context-based loading patterns driven entirely by semantic elements and ARIA attributes — no extra classes required.

1. Indeterminate spinner — <progress> (no value)

Omit the value attribute to switch a <progress> into a compact circular spinner. Use a <label> or aria-label to label it for assistive technology.

2. Determinate progress — <progress value max>

When both value and max are present the element renders as a familiar linear progress bar.

3. Inline action spinner — button[aria-busy="true"]

Set aria-busy="true" on a <button> to append an inline spinner after the label. The label text stays visible so the action meaning remains clear. Pair with disabled when repeat submission must be prevented.

Spinner styling is intentionally scoped to <button>. input[type="submit"] and similar replaced controls do not support ::after reliably across browsers.

4. Busy-region overlay — :where(form, fieldset, section, article, main, aside, dialog)[aria-busy="true"]

Set aria-busy="true" on a semantic sectioning or form element to dim its content and render a centered overlay spinner. No extra wrapper markup or classes are needed. The overlay is purely decorative; authors remain responsible for live-region copy (role="status" or role="alert") where AT announcements are required.

Toast notifications

Transient, non-blocking notifications rendered in a fixed top-end stack. Presentation only — application code owns insertion, removal, queueing, timing, and focus management. For blocking or form-local feedback, use inline messages or a <dialog> instead.

The region below is positioned statically inside the showcase for demonstration. In a real application the <aside> sits directly in <body> and is fixed to the viewport corner.

Authoring contract

Wrap all toasts in aside[data-toast-region][aria-label] containing exactly one <ul> or <ol>. Each toast is a direct <li> child. Inside the <li>, place a <div role="status"> (polite announcement) or <div role="alert"> (assertive announcement) that wraps the toast content. The <li> is the CSS styling host; the inner <div> is the live-region host. This keeps ARIA roles valid — role="status|alert" is not permitted on <li>. Add data-tone="success|warning|danger" on the <li> to refine visual meaning without changing announcement urgency.

Two optional button roles are supported inside each toast:

  • button[type="button"][data-dismiss] — close icon, absolutely positioned in the top-inline-end corner. Application code removes the <li> on click. Requires an aria-label for screen-reader users (e.g. aria-label="Close").
  • button[type="button"] (no data-dismiss) — trailing call-to-action, bottom-aligned. Use for contextual actions like "Retry" or "Review storage".

Notification center

A persistent, browsable notification-center panel for production apps that need a stable inbox alongside the transient toast stack. Presentation only — lumen.css styles the panel but does not own notification retrieval, unread counts, mark-read behaviour, item dismissal, or persistence.

This surface is not a live-region toast queue. Use aside[data-toast-region] for transient, auto-announced feedback. Use this surface for a browsable notification inbox that users open on demand.

Populated example

Host is aside[data-notification-center] with aria-label or aria-labelledby. The optional <header> holds a title and a "Mark all read" action. Each <li> may carry data-unread="true" for the unread state and data-tone="success|warning|danger" for semantic tone. The optional <footer> hosts a "View all" link.

An accessible panel-switching primitive for settings screens, detail views, and dashboard sections. Scope is intentionally restricted to section[data-tabs] — it does not affect other <section> elements.

Authoring contract

The host is section[data-tabs]. The direct child tablist is [role=tablist] with either aria-label or aria-labelledby. Each tab trigger is a button[role=tab] carrying aria-controls and aria-selected. Each panel is [role=tabpanel] with an id and aria-labelledby pointing to its tab trigger.

Contract rules

  • The only supported host is section[data-tabs].
  • The host contains exactly one direct [role=tablist] with either aria-label or aria-labelledby.
  • Tab triggers are button[role=tab] — not links; this pattern is for in-page panel switching, not route navigation.
  • Each button carries aria-controls (matching panel id) and aria-selected="true|false".
  • Each panel carries role=tabpanel, a unique id, and aria-labelledby pointing to its tab trigger's id.
  • Inactive panels are hidden by the native hidden attribute — toggled by application code.
  • data-variant="segmented" is a visual variant of the same ARIA contract; it is not a separate component or public API.

Keyboard and application responsibilities

lumen.css styles the ARIA states only. Application code owns:

  • Arrow-key navigation — ArrowLeft / ArrowRight move focus between tab triggers.
  • Roving tabindex — the active tab has tabindex="0"; all others have tabindex="-1".
  • Tab activation strategy — automatic (activate on focus) or manual (activate on Enter / Space).
  • Panel visibility — toggling the hidden attribute on [role=tabpanel] elements.
  • ARIA state — setting aria-selected="true|false" on tab triggers when switching panels.

<form data-form-errors>

  <!-- Summary host: role="alert" for assertive announcement; "status" for polite -->
  <div data-form-summary role="alert" aria-labelledby="summary-heading">
    <h2 id="summary-heading">2 errors prevented this form from being submitted</h2>
    <ul>
      <li><a href="#email">Email address — enter a valid email address</a></li>
      <li><a href="#contact-legend">Preferred contact — select at least one option</a></li>
    </ul>
  </div>

  <!-- Invalid text field -->
  <div data-field>
    <label for="email">Email address</label>
    <input
      id="email"
      type="email"
      aria-invalid="true"
      aria-describedby="email-error"
    />
    <span data-error id="email-error">Enter a valid email address.</span>
  </div>

  <!-- Invalid grouped fieldset — aria-invalid on the fieldset adds group-level emphasis -->
  <fieldset data-field aria-invalid="true" aria-describedby="contact-error">
    <legend id="contact-legend">Preferred contact</legend>
    <label><input type="checkbox" /> Email</label>
    <label><input type="checkbox" /> Phone</label>
    <span data-error id="contact-error">Select at least one contact method.</span>
  </fieldset>

</form>

Contract rules

  • data-form-errors must be placed on the <form> element to activate the summary styles.
  • [data-form-summary] must be a direct child of form[data-form-errors].
  • role="alert" (assertive) or role="status" (polite) is required on [data-form-summary] — the right choice depends on whether the summary appears dynamically after submit.
  • [data-form-summary] must contain exactly one heading child (h2, h3, or h4) and one direct <ul> or <ol>.
  • Each list item must contain an anchor (<a href="#id">) targeting the id of an invalid control or a grouped legend.
  • Grouped fieldset errors extend fieldset[data-field] — add aria-invalid="true" to the <fieldset> itself for group-level border and legend emphasis. Individual controls inside continue using their own aria-invalid / :invalid styling.
  • Link all invalid controls and invalid fieldsets in the summary list; orphaned summary links or missing ids break keyboard navigation.

Accessibility guidance

  • Use role="alert" when the summary is injected after a submit attempt so screen readers announce it immediately.
  • Use role="status" when validation feedback is non-blocking and a polite announcement is appropriate.
  • Move focus to the summary heading or the first invalid field after a failed submit — this is application-owned behaviour.
  • Do not place data-form-summary inside a scroll container; keep it in the natural document flow so it is reached by keyboard navigation.
  • Combine with aria-describedby on each control so field-level error messages are read by screen readers independently of the summary.
